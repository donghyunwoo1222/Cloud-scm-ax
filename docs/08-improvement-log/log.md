## 2026-11-11 · 임시 비밀번호 최초 변경 (#169)

- 문제 → 관리자가 정한 임시 비밀번호를 직원이 계속 쓸 수 있었고, 비밀번호 변경 기능도 없었다.
- 원인 → 계정 생성이 비밀번호를 정하는 것으로 끝났고 "바꿔야 함" 상태를 저장하거나 강제하는 곳이 없었다.
- 해결 → `users.must_change_password`를 추가하고 직원 생성 때 참으로 시작한다. 참인 동안 서버(`get_current_user`)가 `/me`·변경·로그아웃 외 API를 403으로 막고, `POST /auth/password`와 `/change-password` 화면(새 비밀번호 두 번 입력)을 만들었다. 화면 이동만 쓰지 않은 이유는 API 직접 호출로 우회되기 때문이다.
- 결과 → 자동 테스트 3개 추가(차단·해제·옛 비밀번호 무효, 규칙 위반 시 표시 유지, 가입 관리자·기존 계정 미강제), 전체 368개 통과. 로컬 서버에서 임시 계정의 `/products`가 403인 것을 확인했다.
- 확인 못 한 것 → 화면 이동·변경 화면은 3004 개발 서버가 새 경로를 못 읽어(404) 브라우저로 보지 못했다(타입 검사만 통과).

## 2026-11-11 · 로그인 시도 제한 (#168)

- 문제 → 로그인 실패 횟수 제한이 없어 공개 서비스에서 비밀번호 대입 공격에 약했다.
- 원인 → 로그인 API가 실패를 세지 않았다. 계정(users 행) 기준으로 세면 존재하는 이메일만 잠겨서 잠김 여부로 가입 여부가 드러난다. IP 기준은 요청이 Next.js를 거쳐 와서 모두 같은 IP로 보여 쓸 수 없다.
- 해결 → 입력한 이메일 글자를 키로 서버 메모리에서 센다(`app/auth/lockout.py`). 5회 연속 실패하면 15분 잠그고(임시 확정), 잠금 중엔 맞는 비밀번호도 429 한 문구로 막는다. 성공하면 0으로, 마지막 실패 후 15분이 지나면 새로 센다. 없는 이메일도 똑같이 센다.
- 결과 → 자동 테스트 4개(잠금·해제, 있는/없는 이메일 응답 동일, 성공 시 초기화, 오래된 실패 잊기, 시간은 고정). 한계: 재시작 초기화·다중 서버 미공유, 남이 내 이메일을 일부러 잠글 수 있음.

## 2026-11-07 · 모바일 입력칸 시험 적용: 테두리에 걸친 라벨 (#141)

- 문제 → 라벨이 입력칸 위에 따로 한 줄을 차지해 항목마다 약 25px가 더 들고, 폼마다 입력칸 오른쪽 끝이 제각각(메모 칸 320px 제한 등)이라 비율이 맞지 않아 보였다.
- 원인 → 라벨 글자가 `<label>` 안의 맨 글자라 위치를 바꿀 수 없었고, 폼 항목은 기본 폭(150~320px)으로 줄바꿈만 했다.
- 해결 → 라벨 글자를 span 으로 감싼 `Field` 컴포넌트(`lib/field.tsx`)를 만들었다. 데스크톱(730px 이상)은 지금처럼 라벨이 입력칸 위이고, 모바일에서는 라벨이 위쪽 테두리에 걸린다(라벨 뒤 배경은 위쪽 절반 투명 + 아래쪽 절반 카드색이라 카드 안이든 페이지 배경 위든 테두리가 깨끗이 끊긴다). 포커스는 바깥 윤곽선(라벨 글자를 가로지른다) 대신 파란 테두리 + 안쪽 1px 선과 파란 라벨로 바꿨다. 품목·입고·출고 폼에만 적용했고 품목 선택칸은 라벨을 왼쪽, 현재고 칩을 오른쪽 테두리에 걸었다. 긴 라벨은 모바일에서만 짧게 보인다(`재고 단위 단가(원)*` → `단가(원)*`, `박스당 구매 단가(원)` → `박스 단가(원)`). 줄 사이 간격은 라벨이 올라오는 만큼 18px.
- 결과(로컬 시드, 375px) → 품목 등록 폼 424px → 354px(박스 설정 접힘, −17%), 펼치면 559px → 476px(−15%). 처음(807px)에 비하면 −56%. 360px에서도 같은 높이이고 라벨이 잘리지 않는다. 430px에서 모든 입력칸 오른쪽 끝이 폼 가장자리에 맞는다. 가로 넘침 없음. 출고 등록에서 판매 1개를 실제로 등록해 저장 동작을 확인했다. 1280px에서는 라벨이 입력칸 위(정적)이고 항목 간격 16px, 박스 입수·단가가 그대로 보인다.
- 점검 중 찾은 것 → ① 실사 조정의 `방향` 선택지("감소 (실제가 더 적음)")가 두 칸 폭에서 잘려 조정일 때는 한 줄 전체 폭으로 했다. ② 바깥 윤곽선이 라벨 글자를 가로질러 포커스 표시를 안쪽 선으로 바꿨다. ③ 메모 옆 등록 버튼의 위쪽 간격 규칙(라벨 높이만큼 내림)이 라벨이 없어진 모바일에서는 어긋나 풀었다.

### A. 현재고와 진행 중 수량을 서로 다른 순간에 읽음

- 결과: Node로 최대 줄 금액, 일반 숫자의 안전 정수 범위를 넘는 합계, 서울 날짜 기준 납기 경계를 확인했다.

## 2026-11-05 · 발주서 상세에서 미입고 품목 찾기 (#93)

- 문제: 부분 입고된 발주서에서 잔량이 있는 품목을 찾으려면 품목 표 전체를 읽어야 했다.
- 원인: 품목 표가 모든 줄을 등록 순서로만 표시했다.
- 해결: 발주함 상태에서 남은 수량이 있는 줄만 표시하거나 품목명을 가나다순으로 정렬할 수 있게 했다. 표에 그릴 배열만 가공하고, 입고 폼을 여는 동안 선택을 잠근다.
- 결과: Node에서 전량 2줄과 부분 1줄 중 부분 1줄만 남고, 전체 금액은 370,000원이며 원본 순서가 유지됨을 확인했다. 정렬 양방향·동일 이름·빈 결과도 확인했다. 브라우저에서의 입고 등록은 사용자 확인 항목이다.

- 사용자 확인 후속 수정: 품목 보기의 두 선택지를 표 위에 항상 표시했다. 입고 폼은 카드로 묶고 날짜 폭을 줄여 입력칸과 버튼을 나란히 배치했다. 좁은 화면에서는 버튼 묶음이 다음 줄로 내려간다.
- 사용자 확인 후속 수정: 필터·정렬·표시 개수가 흩어져 보여 품목 표에 붙는 도구막대로 묶었다. 선택한 필터에 체크를 표시하고, 정렬은 옵션 폭에 맞추고, 표시 개수는 오른쪽으로 정렬했다.
- 사용자 확인 후속 수정: 발주 전 검토와 입고 완료·취소된 발주서의 품목 찾기에도 쓸 수 있도록 정렬을 모든 상태에 제공했다. 미입고 필터는 받을 품목이 남을 수 있는 발주함 상태에 둔다.
