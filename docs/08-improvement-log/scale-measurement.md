# 규모 측정 결과 (#184 PR 2)

품목 3,000개 규모에서 주요 API의 **서버 처리 시간**을 쟀다. 서버 코드는 바꾸지 않았다. 기준: 2초 초과면 "느림"(사용자 결정). 스크립트와 실행 방법은 `backend/perf/`(README 참고, CI에는 들어가지 않는다).

## 데이터와 방법
- 회사 X: 품목 3,000, 공급업체 40, 입출고 이력 300,000(품목당 100건: 판매 90·중간 입고 8·폐기 1·최초 입고 1), 과거 발주서 1,500. 회사 Y(다른 회사 섞기): 품목 600, 이력 60,000. 측정은 X로만 했다.
- 재고 = 이력 합계 규칙: 최초 입고량을 `출고 합계 − 중간 입고 합계 + 목표 재고`로 넣고, 삽입 뒤 음수 재고 0개·목표와 다른 재고 0개를 검증했다(통과).
- 읽기 5회(첫 호출은 워밍업, 중앙값·최댓값은 나머지 4회), 쓰기 3회(입력은 매번 다르게, 반복 사이의 측정용 초안 삭제는 시간에서 뺐다). `TestClient`로 직접 호출, `scm_test`에서만.

## #211 뒤: 판매 가져오기 확정 (2026-11-12, 전용 DB `scm_test_sales_import`, 같은 스크립트·같은 데이터)

**문제 → 원인 → 해결 → 결과**
- 문제: 5,000행 확정이 10~22초(2초 기준 초과).
- 원인: 느린 쿼리가 아니라 쿼리 개수. 줄마다 `register_movement`가 품목 잠금·현재고 합계·저장 3쿼리를 실행했다. 바꾸기 전 재측정에서도 가장 느린 한 문장이 60ms였고, 평균 약 0.8ms짜리 왕복이 15,000번 쌓였다. 실행마다 흔들리는 것(10.7초·12.5초·22초)도 왕복 횟수에 컴퓨터 부하가 곱해진 것으로 본다(증명은 확인 못함).
- 해결: 잠근 뒤 계산하는 `analyze`가 이미 품목별 재고를 한 번에 읽고 (날짜, 행) 순서로 메모리에서 누적해 음수 줄을 거른다. 그래서 줄마다 다시 잠그고 합계를 낼 필요가 없다. `stock.register_movements`가 ① 회사 조건을 건 번호순 재잠금 ② INSERT 한 번 ③ 저장 뒤 품목별 재고 한 번 확인(0 미만이면 409)으로 쓴다. 한 호출의 줄은 방향이 모두 같아(판매는 모두 OUT) "마지막 재고 ≥ 0"이면 "중간 재고도 모두 ≥ 0"이다. 그래서 끝에 한 번 확인한 것과 줄마다 확인한 것의 판정이 같다.
- 결과:

| 판매 가져오기 확정(5,000행) | 쿼리 수 | 워밍업 | 중앙값 | 최댓값 | 2초 초과 |
| --- | ---: | ---: | ---: | ---: | --- |
| 바꾸기 전(같은 날 재측정) | 15,006 | 14.00s | 12.47s | 13.02s | 초과 |
| 바꾼 뒤 | **9** | 0.89s | **1.02s** | 1.05s | 아니오 |

- 바꾼 뒤 가장 오래 걸린 문장은 5,000행 INSERT(418ms), 이미 반영된 주문번호 조회(146ms), 재고 합계(79ms) 순이다. 쿼리 9개 = 로그인 사용자 1 + 잠금 1 + 분석 읽기 4 + 재잠금 1 + INSERT 1 + 재고 확인 1. 행 수와 상관없다(테스트: 10행·300행 모두 8개, 사용자 조회 제외).
- 같은 실행의 다른 항목은 앞 표와 비슷했다(미리보기 0.33s, 초안 1,000품목 1.53s, 발주서 2,000줄 0.56s). 측정 전후 표 8개 행 수는 모두 0으로 같았다.
- 비동기 전환은 필요 없다(2초 이하).

## 2초를 넘은 곳: 판매 가져오기 확정 (#211 전 기록)
- 쿼리 15,006개 = 5,000행 × 3(품목 잠금 + 현재고 합계 + 이력 저장). 줄마다 `register_movement`(음수 재고 검사 때문에 품목 잠금·합계를 매번 한다)를 부르는 구조(`services/sales_import.py` `commit` ③, `services/stock.py`)다.
- 원인 후보: 쿼리 수(파이썬 루프). 인덱스 문제로 보이지는 않는다(가장 오래 걸린 한 문장이 약 80ms, 나머지는 같은 모양의 작은 문장의 반복).
- 고치지 않았다(측정 전 최적화 금지).

## 2초에 가까운 곳: 추천 → 초안 1,000품목 (1.5초)
쿼리 94개, 가장 오래 걸린 것은 `purchase_order_items` INSERT(약 0.1초). 지금은 2초 안쪽이지만 업체당 줄이 더 많아지거나 컴퓨터가 느려지면 넘을 수 있다. 느림은 아니라 후속 이슈로 만들지 않고 주의로만 둔다.

| 후보 | 판정 | 근거 |

## 후속 이슈 초안 (등록 대기, 사용자가 정한다)
**1. [규모] 판매 가져오기 확정을 줄마다 3쿼리에서 품목 단위로 줄이기** → #211로 처리(위 "#211 뒤")
- 원인 후보: 줄마다 잠금·합계·저장(15,006쿼리, 5,000행에 10~22초).
- 방향: 쿼리 합치기 한 가지만. 품목 번호 순으로 이미 잠그므로 품목당 현재고 합계를 한 번만 읽고 메모리에서 누적해 음수 검사를 하고, 저장은 묶어서 한다.
- 하지 않는 것: 비동기, 작업 큐, 규칙 변경(음수 재고 금지·이력 수정 불가·(날짜, 줄) 순서). 합친 뒤에도 2초를 넘으면 그때 비동기(BackgroundTasks와 작업 상태 표 먼저, 새 라이브러리는 제안만)를 별도 이슈로 검토한다. 미리보기 쪽은 이미 0.3초다.
- 완료 기준: 같은 5,000행 데이터(`perf/`)에서 확정이 2초 이하, 쿼리 수가 줄어든다. 기존 가져오기 테스트와 재고 음수 방지·정정 규칙 테스트가 통과한다. 동시 가져오기 잠금 순서는 그대로다.
- 꼭 알기 후보: "줄마다 검사"를 "품목당 한 번 + 메모리 누적"으로 바꿔도 결과가 같은 이유(품목 잠금이 먼저라 그 사이 재고가 안 바뀐다). 예상 질문: "쿼리를 줄이면서 음수 재고 검사의 정확성을 어떻게 지켰나요?"

**2. (주의, 선택) 추천 → 초안 1,000품목이 2초에 가까움** — 1.5초, 쿼리 94개. 1번을 처리한 뒤 같은 스크립트로 다시 재고, 2초를 넘으면 INSERT 묶기 등을 검토한다.

## 측정 한계
- 서버 처리 시간만 쟀다. 브라우저·네트워크·Next.js 시간과 동시 사용자는 포함하지 않았다.
- DB는 로컬 Docker 한 대라 운영 환경과 다를 수 있고, 데이터는 합성이라 실제 분포와 다르다. 품목 3만 개(10배)는 재지 않았다.
- 같은 데이터에서도 실행마다 시간이 최대 2배 흔들렸다(위).

## 데이터 정리 (알려야 할 문제)
- 앞선 실행들은 `finally`로 측정용 회사를 지웠고 행 수가 시작 때와 같았다(모든 표 0행).
- **마지막 실행은 중간에 멈췄고, 그 뒤의 정리 DELETE가 끝나지 않아 `scm_test`에 측정용 회사 2곳(이력 375,000건)이 남아 있다.** 개발 DB(`scm`)는 건드리지 않았다. 다음 `pytest` 실행이 `scm_test`의 표를 모두 다시 만들 때 사라진다. 스크립트도 시작할 때 먼저 정리한다.
- 정리가 오래 걸린 원인은 확인하지 못했다. `inventory_movements.reverses_movement_id`에 인덱스가 없어 대량 삭제의 외래키 확인이 느렸을 수 있다(추측). 운영에는 삭제 기능이 없어 영향이 없다.
