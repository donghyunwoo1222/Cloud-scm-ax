## 정해진 공통 규칙 (구현 중 결정)

- 목록 API: `meta {page, page_size, total}`, `page_size` 기본 20·최대 100, 최신순, 비활성은 기본 숨김(`include_inactive=true`면 포함), 검색어 `q`의 `%`·`_`는 글자 그대로(#24·#25)
- 정수 칸은 엄격하게 검사한다(`3.0`·`"3"`·`true`는 422). PATCH에서 선택 칸 `null`은 비우기, 필수 칸 `null`은 422(#25·#26)
- 관리자 자기 자신 변경: 다른 활성 관리자가 있으면 허용, 마지막 활성 관리자면 409 `LAST_ADMIN`(#24)
- SKU는 앞뒤 공백을 지우고 대문자로 저장·비교한다. 업체명은 앞뒤 공백만 지우고 대소문자는 구분한다(#26)
- 오류 코드 추가분: `LAST_ADMIN`(#24), `DUPLICATE_NAME`(#25), `DUPLICATE_SKU`(#26). 모든 오류는 `{"error": {"code", "message", "details"}}`, 성공은 `{"data": ...}`
- 공통 장치
  - 인증·권한: `CurrentUser`, `AdminUser`(`app/auth/deps.py`), `validate_password`(`app/auth/security.py`)
  - 회사 분리: `get_owned`(경로 id)·`check_ref`(본문 id)·`scoped`(목록)(`app/services/tenant.py`). service 함수는 `company_id`를 첫 번째 인자로 받는다
  - 목록: `Page`, `paginate`(`app/pagination.py`)
  - 요청 칸 타입·PATCH 규칙: `app/schemas/common.py`(`Name`, `NonNegInt`, `PatchModel` 등)
  - 테스트: `tests/conftest.py`의 `world`(회사 A·B, 관리자·담당자, A업체·B업체), `tests/helpers.py`(`PASSWORD`, `login_as`). 준비 데이터 fixture는 끝에 `session.commit()`
- 프론트 공통 장치(#27)
  - API 호출은 `frontend/app/lib/api.ts`의 `api()` 하나로: 주소는 `/api/v1/...` 상대 경로(rewrites), 성공이면 `data`, 실패면 `ApiError(status, code, message, details)`, 401이면 로그인 화면으로(로그인 요청만 `redirectOn401: false`). 목록의 `meta`가 필요하면 이 함수를 넓혀서 쓴다
  - 로그인 후 화면은 `frontend/app/(app)/` 아래에 둔다. 레이아웃이 `/me`로 로그인을 확인하고, 화면에서는 `useMe()`(확인 전 null)로 내 정보·역할을 읽는다
  - 레이아웃은 로그인 확인 전에도 화면을 그리되 숨긴다(`hidden`). 그리지 않으면 Next.js 16 개발 모드가 instant navigation 경고를 낸다
  - 메뉴 숨김·화면 안내는 편의이고, 권한은 서버가 검사한다
- 시드: `cd backend` 후 `.venv\Scripts\python -m scripts.seed`(지우고 새로 넣기), `--clear`(지우기). 계정은 README 참고(개발용)

## 꼭 알기 모음

형식: 무엇 / 왜(숫자 예시) / 예상 면접 질문

- #19 DB 주소는 실행 위치마다 다르다(Docker 안 `db:5432`, 내 컴퓨터 `localhost:5433`) / 컨테이너끼리는 서비스 이름으로 찾고, 내 컴퓨터는 바깥 포트로만 들어간다. 5432는 이미 설치된 PostgreSQL이 써서 `localhost:5432`로 붙으면 엉뚱한 DB에 연결된다 / "Docker 안의 백엔드와 로컬 테스트가 DB 주소를 다르게 쓰는 이유는?"
- #20 로컬과 CI가 같은 위치(`backend/`)에서 같은 명령(`python -m pytest`, `python -m ruff check .`)을 쓴다 / 명령이 다르면 로컬 1 passed, CI 0개 실행처럼 결과가 갈린다. 같으면 "로컬 통과 = CI 통과"를 믿을 수 있다 / "CI에서만 테스트가 실패하는 일을 어떻게 줄였나요?"
- #20 브랜치 보호에 "통과해야 할 검사" 목록(`backend`·`frontend`)을 직접 지정해야 실제로 막힌다 / 목록이 0개면 통과할 검사도 0개라 CI가 빨간색이어도 머지됐다 / "깨진 코드가 main에 들어가지 않게 어떻게 막았나요?"
- #21 재고는 칸에 저장하지 않고 입출고 이력의 합계로 계산한다 / 입고 320·판매 300·폐기 5면 재고 15. 재고 칸을 따로 두면 저장 실패 한 번에 칸 315·이력 15로 어긋난다. 비용은 매번 합계를 계산하는 것이고, (company_id, product_id, movement_date) 인덱스로 대응한다 / "재고 수량 칸을 두지 않은 이유와, 그 대신 감수한 비용은?"
- #21 잘못 넣은 이력은 지우지 않고 원래 이력을 가리키는 정정 행(`reverses_movement_id`)을 추가하며, 그 연결을 DB CHECK(`chk_movement`)가 강제한다 / 판매 100(#51)을 잘못 넣고 정정 90을 추가하면 재고 변화 −10, 30일 판매 10이 맞고 원래 기록도 남는다. 정정인데 원래 줄 번호가 없으면 DB가 거절한다 / "입출고 이력을 수정·삭제할 수 없게 하면 실수는 어떻게 고치나요?"
- #22 로그인 실패는 이유(없는 이메일·틀린 비밀번호·비활성)와 관계없이 같은 401 문장을 주고, 없는 이메일도 가짜 해시로 같은 시간만큼 검사한다 / 메시지가 갈리면 이메일 1,000개를 넣어 가입된 30개를 골라낼 수 있고, 응답 시간이 0.001초 대 0.05초로 갈려도 같은 정보가 샌다 / "로그인 실패 메시지를 왜 하나로 통일했나요?"
- #22 토큰이 유효해도 요청마다 DB에서 사용자를 다시 읽어 비활성이면 401 / 토큰은 8시간짜리라 오전 10시에 퇴사 처리한 직원도 확인하지 않으면 오후 6시까지 쓸 수 있다. 대신 요청마다 조회가 1번 늘어난다 / "JWT는 서버에 저장하지 않는데, 퇴사자 접근은 어떻게 바로 막나요?"
- #22 로그아웃은 쿠키를 지울 뿐이라 JWT는 만료(8시간)까지 유효하다 / 토큰이 유출되면 최대 8시간 쓸 수 있다. httpOnly(화면 스크립트가 못 읽음)로 유출 자체를 줄이고, 만료 8시간으로 피해 시간을 묶고, 비활성 즉시 차단으로 사람 단위로 끊는다 / "JWT 로그아웃의 한계와 어떻게 보완했나요?"
- #23 없는 id와 다른 회사 id에 똑같은 404를 준다(code·message·details 모두 같음) / 403을 주면 1번부터 1000번까지 넣어 보는 것만으로 다른 회사 공급업체가 몇 개인지(예: 57개) 셀 수 있다 / "다른 회사 데이터에 접근하면 왜 403이 아니라 404를 주나요?"
- #23 회사 분리 조건은 `scoped` 한 곳에만 두고 상세(`get_owned`)·참조 검사(`check_ref`)·목록이 모두 이를 거친다(멀티테넌시) / API 20개가 각자 조건을 쓰면 하나만 빠져도 새지만, 한 곳이면 그 한 줄만 지키면 된다. 그 한 줄을 빼 보니 테스트 3개가 바로 실패했다 / "회사별 데이터 분리(멀티테넌시)를 코드에서 어떻게 보장했나요?"
