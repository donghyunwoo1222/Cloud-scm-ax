# 인터뷰 질문지: 중소 공산품·생활용품 유통업체 발주·재고 담당자

Nov 2, 2026 · @우동현

## 인터뷰 목적과 검증할 가설

이 인터뷰는 문제 정의의 persona·pain point와 AX 설계의 가정이 실제 업무와 맞는지 확인하는 자리다. 가설을 뒤받침하려는 것이 아니라 틀렸는지 확인하려는 것이므로, 예상과 다른 답이 나오면 그것이 가장 좋은 결과다.

| 번호 | 가설 | 출처 | 확인 질문 |
| --- | --- | --- | --- |

| H2 | 엑셀·장부 재고와 실제 재고가 맞지 않는다 | pain point #2 | Q3, Q4, Q5 |

persona와 pain point는 가설이고, 특히 A1\~A4는 이 문서에서 처음 세운 가정이다. 인터뷰 결과로 판정하는 방법은 마지막 섹션에 적는다.

## 대상자와 모집

제안서 기준으로 5\~10명을 목표로 하고, 재고·발주 업무를 실제로 해본 사람을 우선한다. 문제 정의의 주 대상은 온라인 판매를 병행하는 직원 5\~30명 도소매 유통업체(로트·유통기한 관리가 필요 없는 공산품·생활용품을 다루는 곳)다. 대상자 구성과 인원은 이 문서에서 제안하는 값이다.

| 역할 | 목표 인원(제안) | 주로 확인할 것 |
| --- | --- | --- |
| 구매·재고 담당 | 3\~5명 | 발주 결정, 재고 파악, 리드타임, 추천에 대한 반응 (MVP 주 사용자) |
| 대표 | 1\~3명 | 발주 승인 방식, 도입 결정 기준 |
| 창고 담당 | 1\~2명 | 입고·출고 기록, 실제 재고와 장부의 차이 |

해당 역할을 구하기 어려우면 소규모 쇼핑몰 운영자, 스마트스토어 셀러, 매장 근무 경험자로 넓히되, 주 대상과 거리가 있다는 점을 기록에 남긴다. 그 결과는 가설 판정에서 따로 표시한다.

### 모집 방법

1. 지인 중 물류·구매·매장 운영 경험이 있는 사람에게 바로 부탁한다.
2. 부트캠프 동료와 튜터에게 주변에 재고·발주 업무를 하는 사람이 있는지 소개를 부탁한다.
3. 온라인 셀러 커뮤니티에 글을 올릴 때는 그 커뮤니티의 규칙(홍보·모집 글 허용 여부)을 먼저 확인한다.
4. 한 명을 인터뷰할 때마다 "비슷한 업무를 하는 분을 소개해 주실 수 있나요?"라고 묻는다.

인터뷰에서 "나중에 만들면 한번 써봐 주실 수 있나요?"(Q25)라고 물어보면, 사용자 테스트 참가자를 따로 구하지 않아도 된다.

### 참여 요청 문구 예시

```markdown
안녕하세요, ○○입니다. 저는 중소 공산품·생활용품 유통업체의 재고·발주 업무를 돕는 웹 서비스를 개인 프로젝트로 만들고 있습니다. 실제 업무가 어떻게 이뤄지는지 알고 싶어서, 재고나 발주 일을 해보신 분께 30분 정도 이야기를 들려주실 수 있는지 부탁드립니다. 서비스를 홍보하려는 자리가 아니고, 회사 내부 자료는 받지 않습니다. 이름과 회사명은 기록하지 않고, 녹음은 동의하실 때만 하겠습니다. 가능한 시간을 알려주시면 맞추겠습니다.
```

문구에 적은 약속(이름·회사명 미기록, 녹음 동의)은 실제로 지킬 수 있을 때만 남기고, 참가자는 P1, P2처럼 코드로만 기록한다.

## 진행 방법과 질문 원칙

인터뷰는 1대 1로 30분 안에 끝내고, "어떤 기능이 필요하냐"가 아니라 "지금 어떻게 일하느냐"를 묻는다. 시간 배분은 이 문서에서 제안하는 값이다.

| 순서 | 시간 | 내용 | 질문 |
| --- | --- | --- | --- |
| 1 | 3분 | 소개, 목적 설명, 녹음 동의 확인 | 없음 |
| 2 | 3분 | 배경 이야기 | Q1, Q2 |
| 3 | 14분 | 재고 파악과 발주 결정 | Q3\~Q12 |
| 4 | 5분 | 발주서, 판매 채널, 도구 경험 | Q13\~Q19 |
| 5 | 3분 | 화면 예시에 대한 반응 | Q20\~Q22 |
| 6 | 2분 | 마무리, 테스트 협조 부탁 | Q23\~Q25 |

화면 예시는 반드시 마지막에 보여준다. 먼저 보여주면 그 화면에 맞춰 대답하기 때문에 실제 업무 이야기를 모두 놓친다. 화면은 AX 설계 문서의 추천 목록 항목과 이유 문구 예시를 종이나 슬라이드 한 장으로 준비한다.

### 질문 원칙

- 과거에 실제로 한 일을 묻는다. "보통 어떻게 하세요?"보다 "가장 최근에 하신 일을 처음부터 말씀해 주세요"가 더 정확하다.
- 해결책을 먼저 꺼내지 않는다. "추천 기능이 있으면 쓰시겠어요?"는 예의상 "네"가 나오는 질문이라 정보가 없다.
- 유도하지 않는다. "이게 힘드시죠?"처럼 답을 정해 둔 질문은 피한다.
- 답이 짧으면 "왜 그렇게 하셨어요?" 한 번만 더 묻고, 침묵이 생기면 기다린다.
- 숫자는 대략적인 값으로 충분하다. 답을 고쳐 주거나 영업하는 태도는 보이지 않는다.

| 피해야 할 질문 | 대신 묻는 질문 |
| --- | --- |
| 재고 관리가 많이 힘드시죠? | 가장 최근에 재고가 안 맞았던 때를 이야기해 주세요 |
| 자동 발주 추천이 있으면 쓰시겠어요? | 가장 최근 발주를 어떻게 결정하셨는지 처음부터 말씀해 주세요 |
| ERP가 비싸서 안 쓰시죠? | 재고 관리 프로그램을 써보신 적이 있나요? 쓰거나 안 쓰는 이유는요? |
| 발주서 만드는 게 귀찮지 않으세요? | 발주서를 한 장 만드는 데 보통 얼마나 걸리나요? |

## 기록 양식

인터뷰마다 아래 표를 복사해 채운다. 인터뷰 직후 24시간 안에 채워야 기억이 왜곡되지 않는다. 참가자는 이름 대신 P1, P2처럼 코드로만 적는다.

| 항목 | 기록 방법 |
| --- | --- |
| 코드·날짜 | P1, 2026-00-00 |
| 역할 | 담당 / 대표 / 창고 / 그 외(무엇) |

| 재고 기록 도구 | 엑셀, 수기, 프로그램 등 |
| 발주 방식 | 주기, 수량 기준, 발주서 작성·전달 방법, 소요 시간 |
| 리드타임·안전재고 | 일수(업체별 차이), 여유분 유무 |
| 최근 품절·과다 재고 경험 | 상황과 원인을 한두 줄로 |
| 가설 판정 | H1\~H5, A1\~A6 각각 맞음 / 부분 / 틀림 / 모름 중 하나와 근거 한 줄 |
| 인상적인 말(그대로) | 따옴표로 원문 그대로 |
| 새로 나온 pain point | Q23, Q24에서 나온 것 |
| 예상과 다른 점 | 가설과 어긋난 답 |
| 테스트 협조 여부 | 가능 / 불가 / 추후 확인 |

"모름"은 질문을 하지 못했거나 답이 불분명했다는 뜻으로 쓴다. "틀림"이나 "예상과 다른 점"을 비워두지 않도록 의식해서 적는다.

## 인터뷰 후 정리

인터뷰가 5명 쌓이면 중간 점검을 하고, 끝난 뒤에는 가설마다 유지, 수정, 재검토 중 하나로 판정해 문서와 이슈에 반영한다. 아래 기준과 중간 점검 시점은 이 문서에서 제안하는 값이다.

| 판정 | 기준(제안) | 다음 조치 |
| --- | --- | --- |
| 유지 | 인터뷰한 사람 중 과반이 실제 있었던 사례로 확인해 줬다 | 현재 문서 그대로 둔다 |
| 수정 | 일부만 맞거나 역할·규모에 따라 달랐다 | 해당 문서의 내용과 범위를 고친다 |
| 재검토 | 대부분 틀렸거나 실제로는 문제가 아니다 | pain point 우선순위와 MVP 범위를 다시 논의한다 |
| 보류 | 답이 부족하거나 불분명하다 | 다음 인터뷰에서 질문을 보강한다 |

판정에서는 "이런 일이 있을 것 같다"는 의견보다 "지난달에 이런 일이 있었다"는 실제 사례를 더 무걱게 본다. 5\~10명은 통계가 아니라 방향을 확인하는 수준이라, 결과를 "시장의 모든 중소기업이 그렇다"라고 일반화하지 않는다.

### 문서와 이슈에 반영하는 위치

| 결과 | 반영 위치 |
| --- | --- |
| persona·pain point 변경 | 문제 정의 문서(`docs/02-problem-definition/`) 수정 |
| AX 가정(A1\~A4) 변경 | AX 설계 문서의 제안 값(보충 주기, 리드타임 처리 등) 수정 |
| 새 요구사항·불편 | GitHub 이슈(`user-feedback` 라벨) |
| 범위 변경 | 5단계 MVP 범위 문서 |
| 인터뷰 요약 | 포트폴리오 검증 항목에 이름과 회사명을 빼고 코드(P1\~)로만 정리 |

중간 점검은 5명을 끝냈을 때 한다. 이때 질문이 유도적이었는지, 빠진 주제가 있는지 확인하고 질문지를 고친다.
