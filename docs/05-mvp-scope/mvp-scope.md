# MVP 범위 확정: 기능 등급·제외 항목·완료 기준

Nov 2, 2026 · @우동현

## 확정 결정

5단계에서는 AX 설계에 남아 있던 두 가지(이유 문구, 품목의 기본 공급업체)를 정했고, 이를 포함해 MVP 범위를 등급으로 고정한다. 표의 마지막 행만 이 문서에서 처음 낸 제안이다.

| 결정 | 내용 | 정한 단계 |
| --- | --- | --- |
| 대상 업종 | 유통업 우선, 제조업은 확장 시나리오(BOM 관리는 MVP 제외) | 3단계 |
| 판매 채널 | 출고 등록 시 판매 채널만 기록. 판매 주문 기능과 채널 API 연동은 후순위 | 3단계 |
| 일평균 판매량 | 최근 30일 평균 | 4단계 |
| 추천 결과 표시 | 추천 목록 + 발주서 초안(DRAFT) 자동 생성. 승인은 사람이 함 | 4단계 |
| 자연어 질의 | MVP 제외, 후순위 | 4단계 |
| 이유 문구 | 규칙 기반 문장 틀로 시작. LLM으로 문장을 다듬는 것은 선택 기능(Could) | 5단계 |
| 기본 공급업체 | 품목당 공급업체 1개를 지정하는 필드를 포함(한 품목을 여러 업체에서 사는 경우는 다루지 않음) | 5단계 |
| 리드타임 저장 위치 | 공급업체에 저장(0 이상 정수). 품목의 리드타임 = 기본 공급업체의 리드타임. 기본 공급업체는 품목 필수 입력 | 6단계 시작 전(11-03) |
| 출고 유형과 실사 조정 | 출고 유형(판매/폐기·파손/기타)을 구분하고 판매 출고만 일평균에 포함. 실사 차이는 "조정" 이력(사유 필수)으로 기록해 재고 = 이력 합계 원칙 유지 | 6단계 시작 전(11-03) |
| 발주 규칙 | 부분 입고 후 취소 불가, 부분 입고 후에도 ORDERED 유지(누적 입고량 = 발주 수량이면 RECEIVED), 초과 입고 차단, 승인 생략 없음 | 6단계 시작 전(11-03) |
| 등급 체계 | Must와 Could만 두고 Should는 두지 않는다(제안). 8주 안에 할 것과 아닌 것을 분명히 나눠 밀림을 막는다 | 5단계 |

## 기능 등급표

MVP에는 Must 8개(F1\~F8)를 반드시 만들고, Could 1개는 일정이 남을 때만 만든다. 등급은 제안서의 구분(필수, AX 필수 후보)을 그대로 이어받았다. 이슈 번호는 GitHub 저장소 기준이다.

| 기능 | 등급 | MVP에 포함하는 범위 | 이슈 |
| --- | --- | --- | --- |
| F1 회사/사용자 | Must | 로그인, 회사 단위 데이터 분리, 역할 3종(관리자, 구매·재고 담당, 창고 담당) | #2 |
| F2 공급업체 | Must | 공급업체 등록·조회·수정, 리드타임(일) 저장 | #3 |
| F3 품목(SKU) | Must | 단가, 안전재고, 기본 공급업체 1개(필수) 저장. 리드타임은 공급업체에 저장하고 품목이 기본 공급업체의 값을 쓴다 | #4 (11-03 반영 완료) |
| F4 입고/출고 | Must | 수량 변경과 이력 기록, 음수 재고 차단, 출고 유형(판매/폐기·파손/기타)과 판매 채널 기록, 실사 차이 조정 이력(사유 필수) | #5 |
| F5 현재 재고 | Must | 품목별 현재고와 상태 표시, 이력 합계와 일치 | #6 |
| F6 발주 | Must | 상태 흐름(DRAFT → APPROVED → ORDERED → RECEIVED/CANCELLED), 입고 연결, 납기·단가 이력 | #7 |
| F7 대시보드 | Must | 재고 부족, 장기재고, 이번 달 입출고 현황 | #8 |
| F8 발주 추천(AX) | Must | 규칙 기반 계산, 추천 목록, 이유 문장, 발주서 초안 자동 생성 | 새 이슈(`ax`) |
| C1 이유 문구 LLM 다듬기 | Could | 계산 결과는 그대로 두고 설명 문장만 자연스럽게 변환 | 새 이슈(`ax`) |

F8은 제안서에서 "AX 필수 후보"였던 것을 4단계 AX 설계에서 필수로 확정한 기능이다. F7의 장기재고 기준은 아직 정해지 않았고, 구현 전에 정해야 한다.

## MVP에서 제외하는 것

아래 항목은 MVP에서 만들지 않는다. 범위 밖 기능을 만들자는 제안이 나오면 이 표를 기준으로 "MVP 범위 밖"이라고 답한다. 구분은 제안서와 앞 단계 결정을 따른다.

| 항목 | 구분 | 제외 이유 | 출처 |
| --- | --- | --- | --- |
| 자연어 SCM 질의 | 후순위 | 발주 추천을 먼저 완성하고 검증하는 데 집중. company\_id 안전장치가 추가로 필요함 | 제안서, AX 설계 |
| 고급 수요예측 | 후순위 | 충분한 판매 이력과 평가 기준이 필요함 | 제안서 |
| 주간 요약 | 후순위 | MVP 이후 AX 확장 | 제안서(AX 우선순위 4) |
| 공급망 리스크 알림 | 후순위 | 납기 이력이 쌓인 뒤에야 가능 | 제안서(AX 우선순위 5) |
| 판매 주문 기능 | 후순위 | MVP는 출고 시 채널만 기록 | 3단계 결정 |
| 실제 채널 API 연동 | 후순위 | 외부 연동은 범위와 일정 부담이 큼 | 3단계 결정 |
| 제조업 BOM 관리 | 확장 시나리오 | 유통업을 우선 | 3단계 결정 |
| 품목별 보충 주기, 최소 주문 수량 | 후순위(제안) | 테스트 후 필요성 확인 | AX 설계 |
| 한 품목의 여러 공급업체 | 후순위(제안) | MVP는 품목당 기본 공급업체 1개만 | 5단계 결정 |
| 회계·급여·전사 ERP | 제외 | 범위 과다 방지 | 제안서 |

이 항목들은 나중에 "MVP 이후 로드맵" 문서(`docs/10-roadmap/post-mvp-backlog.md`)로 모아 관리한다. 분류 기준은 다르지만 내용이 겹치면 그 문서를 기준으로 맞춘다.

## MVP 완료 기준

아래 체크리스트를 모두 통과하면 MVP가 끝난 것으로 본다. 사용자 테스트를 시작할 수 있는 상태가 기준이며, 항목 구성은 이 문서에서 제안한 것이다.

### 기능과 시나리오

- [ ] F1\~F8 이슈의 완료 기준을 모두 충족하고 이슈가 닫혀 있다
- [ ] 대표 시나리오(품목 등록 → 입고 → 출고 → 부족 확인 → 발주 생성)를 처음부터 끝까지 오류 없이 수행할 수 있다
- [ ] 발주 추천 목록에서 공급업체별 발주서 초안(DRAFT)까지 만들 수 있다

### 데이터 원칙

- [ ] 다른 회사의 데이터는 조회·수정할 수 없다(company\_id)
- [ ] 현재고보다 큰 출고는 막히고 재고는 음수가 되지 않는다
- [ ] 현재고가 입출고 이력 합계와 항상 일치한다
- [ ] 발주 상태는 허용된 순서로만 바뀔고, 승인(APPROVED)은 관리자만 할 수 있다

### 검증과 배포

- [ ] 발주 추천 정답 시나리오 S1\~S11이 자동 테스트로 통과한다
- [ ] 공개 데이터 점검을 한 번 실행하고 결과를 기록했다
- [ ] 서비스 URL에서 로그인부터 대표 시나리오까지 동작한다
- [ ] 사용자 테스트 참가자에게 줄 테스트 계정과 샘플 데이터가 준비되어 있다

### 프로젝트 마무리(8주차)

아래는 MVP 완료 후 포트폴리오 증빙을 갖추는 기준이고, 제안서의 최종 증빙 항목을 따른다.

- [ ] GitHub 저장소와 README(서비스 URL, 실행 방법 포함)
- [ ] ERD와 아키텍처 다이어그램
- [ ] 시연 영상
- [ ] 사용자 테스트 결과(5\~10명)
- [ ] 개선 기록(문제 → 원인 → 해결 → 결과)

## 일정과 범위 조정 규칙

일정은 제안서의 8주 계획을 그대로 따른다. AI 도구로 코딩이 빨라질 수 있지만 실제 속도는 해봐야 알 수 있어서, 일정을 줄이지 않고 3주차가 끝날 때 속도를 확인해 다시 정한다(제안).

&#91;embedded content: 8주 로드맵 · 작업 7개, 점검 시점 2개\]

3주차 끝에서는 DB·API·CRUD가 예상보다 빨랐는지 느렸는지를 보고 남은 주를 조정하고, 7주차 끝에서는 MVP 완료 기준을 확인한다. 빨라진 시간은 일정 단축이 아니라 인터뷰·사용자 테스트·AX 고도화·문서 품질에 쓴다.

### 일정이 밀릴 때 줄이는 순서(제안)

1. C1(이유 문구 LLM 다듬기)를 하지 않는다. 원래 Could라 영향이 없다.
2. F7 대시보드를 재고 부족 목록 중심으로 단순화한다(장기재고 등 보조 표시는 뒤로 미뢬다).
3. 그래도 밀리면 Must 범위를 다시 논의한다. Must 기능을 조용히 줄이지 않고, 이 문서를 고쳐 어떤 기능을 빼는지 기록한다.
