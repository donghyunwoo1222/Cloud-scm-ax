# 규모 측정 스크립트 (#184)

품목 3,000개·입출고 이력 약 30만 건 규모에서 주요 API의 **서버 처리 시간**을 잰다. 서버 코드는 바꾸지 않고, CI의 pytest에도 들어가지 않는다(`tests/` 밖, `pytest.ini`의 `testpaths = tests`).

## 실행 방법

`backend/` 폴더에서 (로컬 Docker DB가 5433 포트로 떠 있어야 하고, 표는 pytest를 한 번 돌려 만들어 둔 `scm_test`에 있어야 한다). 다른 작업과 겹치지 않게 `scm_test_<이름>` 전용 DB(예: `scm_test_sales_import`)도 쓸 수 있다(#211, pytest와 같은 이름 규칙). 그 DB를 `TEST_DATABASE_URL`로 pytest를 한 번 돌려 표를 만든 뒤 아래 주소의 DB 이름만 바꾼다:

```bash
DATABASE_URL=postgresql+psycopg://scm:scm_local_pw@localhost:5433/scm_test \
SECRET_KEY=ci-only-test-secret-not-used-anywhere-else \
python -X utf8 -m perf.measure_scale
```

- #211 전에는 약 8~10분 걸렸다(판매 가져오기 확정 5,000행 × 3회가 대부분). #211 뒤 확정은 회당 약 1초로 줄었지만, 전체는 여전히 길다(2026-11-12 실행 약 31분, 그중 끝의 정리 단계 이력 DELETE가 약 25분). 정리가 느린 원인은 정정 칸(`reverses_movement_id`)에 인덱스가 없어 줄마다 외래키 확인이 표 전체를 훑기 때문으로 추정한다(확인 못함). 결과는 화면에 마크다운 표로 나온다. 파일로 남기려면 `> result.txt`를 붙인다.
- 느린 문장의 EXPLAIN도 함께 보려면 끝에 `--explain-all`을 붙인다.
- 입고 가져오기 확정 5,000행만 재려면 끝에 `--only receipt-import`를 붙인다(#222). 품목 3,000개만 만들고 과거 이력은 넣지 않아 약 1분 안에 끝나고 정리도 몇 초다. 이 옵션이 없으면 전체 측정은 그대로다.

## 반드시 지킬 것

- **측정하는 동안 pytest를 돌리지 않는다.** pytest는 시작할 때 `scm_test`의 표를 모두 지우고 다시 만든다. 같이 돌면 측정이 깨진다.
- **개발 DB(`scm`)에는 쓰지 않는다.** 스크립트는 DB 이름이 `scm_test` 또는 `scm_test_<이름>`이 아니면 아무것도 하지 않고 멈춘다. 표를 만들거나 지우는 코드(`reset_database`, `downgrade`)도 쓰지 않는다.
- `seed.py`와 상관없다. 스크립트가 만드는 회사는 이름이 `__perf__`로 시작하는 2곳뿐이다.

## 무엇을 하나

1. 시작할 때 이전 실행이 남긴 `__perf__` 회사를 먼저 지우고 표별 행 수를 센다.
2. 회사 X(품목 3,000, 공급업체 40, 이력 약 30만, 과거 발주서 1,500)와 회사 Y(품목 600, 이력 약 6만, 다른 회사 섞기)를 SQL 한 번씩으로 만든다.
   - 품목마다 판매 90줄, 중간 입고 8줄, 폐기 1줄, 최초 입고 1줄(100일 전).
   - 최초 입고량을 `출고 합계 − 중간 입고 합계 + 목표 재고`로 넣어서 **현재고 = 이력 합계**가 목표와 정확히 같다. 삽입 뒤 음수 재고 0개·목표와 다른 재고 0개를 검증하고, 어긋나면 측정하지 않는다.
   - 목표 재고: 짝수 번호 0~10(부족 후보), 5,000 이상(과잉 후보), 나머지 50~200.
3. `ANALYZE`로 통계를 갱신하고, 회사 X 담당자로 로그인해 `TestClient`로 호출한다.
   - 읽기: 같은 조건 5회. 첫 호출은 워밍업이라 따로 표시하고 중앙값·최댓값은 나머지 4회로 낸다.
   - 쓰기(추천 → 초안 1,000품목, 발주서 2,000줄, 판매 가져오기 확정 5,000행): 3회, 입력은 매번 다르게(초안 묶음 위치·수량·주문번호). 읽기를 모두 끝낸 뒤에 한다. 반복 사이의 측정용 초안 삭제는 시간에 넣지 않는다.
4. 끝나면(실패해도 `finally`) `__perf__` 회사와 그 행만 지우고, 행 수가 시작 때와 같은지 출력한다.
5. 2초를 넘는 대상은 가장 오래 걸린 SELECT를 `EXPLAIN (ANALYZE, BUFFERS)`(읽기 전용 트랜잭션)로 본다. 인덱스 후보와 관련된 대상(품목 목록, 발주서 목록, 입출고 이력, 추천)은 항상 본다.

## 한계

- 서버 처리 시간만 잰다. 브라우저, 네트워크, Next.js 시간과 동시 사용자는 재지 않는다.
- DB는 로컬 Docker(한 대)라 운영 환경과 다를 수 있다.
- 데이터는 합성이라 실제 판매 분포와 다르다.
