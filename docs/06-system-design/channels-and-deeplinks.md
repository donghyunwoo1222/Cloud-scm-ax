# 채널별 역할과 알림 → 화면 딥링크 규칙 (#198)

작성 기준: 2026-11-16. 모든 소통을 SCM 안으로 옮기면 현장 담당자가 쓰지 않으므로, 채널마다 하는 일을 정해 둔다. 이 문서는 **역할과 링크 규칙을 정하는 문서**이고, 규칙을 코드로 막는 일은 아직 하지 않았다.

**코드 구현 상태: PR 2 예정.** 아래 규칙 C-(4)~(7)(로그인 후 복귀, 허용 경로 검사)은 아직 코드에 없다. 지금 코드는 로그인 뒤 항상 `/dashboard`로 간다(`frontend/app/login/page.tsx`의 `finish`).

용어: **딥링크**는 알림에서 눌렀을 때 홈이 아니라 해당 업무 화면(예: 발주서 한 장)으로 곧바로 열리는 주소다.

## C. 딥링크 규칙

적용 대상은 업무 알림(슬랙·부족 알림 메일 등)이다. 재설정 메일의 토큰 링크는 위 표대로 예외다.

1. **알림 하나는 업무 화면 하나로 바로 연결한다.** 예) 발주서 알림 → `/purchase-orders/17`. 알림마다 "무엇을 볼지"가 하나라서, 눌렀을 때 홈에서 다시 찾지 않는다.
2. **링크에는 `APP_BASE_URL`(https)과 허용 경로만 둔다. 다른 도메인, 회사 식별값, 토큰, 개인 정보, 쿼리를 넣지 않는다.** 경로의 번호(발주서 17번)는 열람 권한이 아니라 화면 이름일 뿐이다. 열 때마다 서버가 로그인 토큰의 회사로 검사해서, 다른 회사 번호는 404로 막힌다(회사는 항상 토큰에서만 가져온다, CLAUDE.md 데이터 원칙 1).
3. **링크는 읽기 화면만 연다.** 링크를 여는 것만으로 승인·발주·입고 같은 상태 변경이 일어나지 않는다(GET은 읽기만, CLAUDE.md §6).
4. **로그인이 없으면 로그인 화면으로 보내고, 로그인 뒤 원래 화면으로 돌아온다.** 형식은 `/login?next=<원래 경로>`다. 관리자 2단계(메일 인증코드) 단계에서도 `next`가 유지되어야 한다.
5. **`next` 값은 디코딩을 한 번만 한 값에 대해 검사한다.** 입력은 브라우저 주소의 `next` 값을 한 번 디코딩한 문자열이다(원문 `%2Fdashboard` → 검사 대상 `/dashboard`). 한 번 더 디코딩한 값이나 원문을 따로 검사하지 않는다. 두 번 디코딩하면 `%252F` 같은 값이 검사 뒤에 다른 뜻으로 바뀔 수 있어서다.
6. **다음 중 하나라도 해당하면 `next`를 버리고 `/dashboard`로 보낸다.**
   - `/`로 시작하지 않는다(`https://…`, `javascript:…` 포함)
   - 경로에 `..`이 있다
   - 첫 글자 뒤에 `//`가 있다(시작하는 `//`는 다른 사이트 주소로 읽히므로 이 경우도 거절한다)
   - 아래 허용 경로 목록과 일치하지 않는다
   - 쿼리(`?`)나 `#`가 붙어 있다
7. **허용 경로는 아래 14개뿐이다.** 번호 자리(`{id}`)는 숫자만 받는다. 허용 목록은 프런트 실제 라우트(`frontend/app/(app)/**/page.tsx`, 2026-11-16 대조)와 같은 것에서 골랐다. 같은 화면이라도 입력·가져오기 화면은 알림으로 열 이유가 없어 뺐다.

| # | 경로 | 화면 |
| --- | --- | --- |
| 1 | `/dashboard` | 대시보드 |
| 2 | `/inventory` | 재고 현황 |
| 3 | `/recommendations` | 발주 추천 |
| 4 | `/purchase-orders` | 발주서 목록 |
| 5 | `/purchase-orders/{id}` | 발주서 상세 |
| 6 | `/purchase-orders/{id}/document` | 발주서 문서 |
| 7 | `/receipts` | 입고 |
| 8 | `/shipments` | 출고 |
| 9 | `/products` | 품목 |
| 10 | `/suppliers` | 공급업체 목록 |
| 11 | `/suppliers/{id}` | 공급업체 상세 |
| 12 | `/company` | 회사 정보 |
| 13 | `/slack` | 슬랙 연결 |
| 14 | `/users` | 사용자 관리(관리자 전용 화면, 담당자는 화면 안에서 안내 문구만 본다) |

허용 목록에 **없는** 실제 화면(5개, 알림으로 열지 않는다): `/purchase-orders/new`, `/purchase-orders/{id}/edit`, `/product-import`, `/receipt-import`, `/sales-import`. 로그인 전 화면(`/login`, `/forgot-password`, `/reset-password`, `/change-password`)도 `next` 도착지로 쓰지 않는다. 새 화면을 만들 때 알림으로 열어야 하면 이 표에 한 줄을 더한다.

### 규칙 대응 점검(예시, 코드 아님)

| `next` 원문 | 한 번 디코딩한 값 | 결과 |
| --- | --- | --- |
| `%2Fpurchase-orders%2F17` | `/purchase-orders/17` | 허용 |
| `%2Fpurchase-orders%2Fabc` | `/purchase-orders/abc` | 거절(숫자가 아님) |
| `%2F%2Fevil.com` | `//evil.com` | 거절(`//`) |
| `https%3A%2F%2Fevil.com` | `https://evil.com` | 거절(`/`로 시작 안 함) |
| `%2Fdashboard%2F..%2Fusers` | `/dashboard/../users` | 거절(`..`) |
| `%252F%252Fevil.com` | `%2F%2Fevil.com` | 거절(허용 목록과 불일치, 다시 디코딩하지 않는다) |

## D. 알려진 한계

- **임시 비밀번호 계정은 원래 화면으로 복귀하지 않는다.** 로그인 뒤 `(app)/layout.tsx`가 `must_change_password` 계정을 `/change-password`로 보내고, 비밀번호를 바꾸면 `/dashboard`로 간다. 이 흐름에서 `next`는 잃어버린다. 임시 비밀번호는 처음 한 번뿐이라 지금은 받아들인다.
- **슬랙 초안 결과 링크가 전체 목록을 가리킨다.** 초안 여러 장을 한 번에 만들 수 있고 결과 문구에 발주서 번호가 없어서 `/purchase-orders` 목록으로 보낸다. 규칙 C-(1)은 "하나의 화면"이지만, 이 알림은 "발주서 여러 장의 목록"이라는 하나의 화면으로 본다. 발주서 한 장을 가리키게 하려면 만든 발주서가 정확히 한 장일 때만 상세로 보내는 별도 결정이 필요하다.
- **서버와 프런트의 허용 경로 목록을 따로 관리해야 한다.** 서버는 알림 링크를 만들 때, 프런트는 `next`를 검사할 때 같은 14개를 쓴다. 한쪽에만 화면을 더하면 링크가 있는데 로그인 뒤 홈으로 가는 어긋남이 생긴다. 한 파일로 합치는 방법(프런트 코드를 서버가 읽거나 공용 JSON)은 PR 2에서 정하지 않고 둔다.
- **로그인 풀림(401) 이동은 `next`를 붙이지 않는다.** `app/lib/api.ts`의 두 곳(요청 실패, 파일 내려받기 실패)이 `/login`으로만 보낸다. 알림 링크를 열었을 때 이미 로그인이 풀려 있으면 이 경로를 탄다.
- 백슬래시(`\`)를 쓴 `next`(`/\evil.com`)가 브라우저에서 어떻게 읽히는지는 확인 못함. 거절 규칙에 넣을지 PR 2에서 정한다.
