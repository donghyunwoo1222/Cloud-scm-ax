# 서비스 기획: 요구사항·업무 흐름·화면 흐름

Nov 2, 2026 · @우동현

## 기획 범위와 전제

이 문서는 MVP 필수 기능 7개를 어떤 역할이 어떤 업무 흐름과 화면으로 쓰는지 정합니다. 이 문서의 내용이 다음 단계(AX 설계, 시스템 설계)의 입력이 됩니다.

| 확정 항목 | 내용 |
| --- | --- |
| 대상 업종 | 유통업 우선, 제조업은 확장 시나리오 (BOM 관리는 MVP 제외) |
| 판매 채널 | 출고 등록 시 채널만 기록. 판매 주문 기능과 채널 API 연동은 후순위 |
| MVP 기능 | 회사/사용자, 공급업체, 품목, 입출고, 현재 재고, 발주, 대시보드 |
| 제외 | 회계·급여·전사 ERP, 고급 수요예측 |

페르소나와 pain point는 여전히 가설입니다. 인터뷰 결과로 내용이 바뀌면 이 문서의 요구사항도 함께 고칩니다.

## 사용자 역할과 권한

MVP는 역할 3개(관리자, 구매·재고 담당, 창고 담당)로 시작합니다. 문제 정의의 persona 3명(박정호, 김서연, 이민수)이 각각 여기에 대응합니다. 세 역할 모두 같은 회사(company\_id)의 데이터만 볼 수 있습니다.

| 역할 | 대응 persona | 주된 업무 |
| --- | --- | --- |
| 관리자(대표) | 박정호 | 사용자 초대, 발주 승인, 대시보드 확인 |
| 구매·재고 담당 | 김서연 | 품목·공급업체 관리, 발주 작성, 재고 확인 |
| 창고 담당 | 이민수 | 입고·출고 등록, 재고 조회 |

기능별 권한은 아래와 같습니다. "조회"는 보기만, "등록·수정"은 만들고 고치기, "승인"은 발주를 확정하는 권한입니다.

| 기능 | 관리자 | 구매·재고 담당 | 창고 담당 |
| --- | --- | --- | --- |
| 사용자 초대·관리 | 등록·수정 | - | - |
| 공급업체 | 등록·수정 | 등록·수정 | 조회 |
| 품목 | 등록·수정 | 등록·수정 | 조회 |
| 입고 | 등록·수정 | 등록·수정 | 등록 |
| 출고 | 등록·수정 | 등록·수정 | 등록 |
| 현재 재고 | 조회 | 조회 | 조회 |
| 발주 작성 | 등록·수정 | 등록·수정 | - |
| 발주 승인 | 승인 | - | - |
| 대시보드 | 조회 | 조회 | 조회 |

이 권한 표는 초안이며, 인터뷰에서 "실제로는 누가 발주를 승인하는지"를 확인해 다듬습니다. 직원 5\~30명 규모에서는 대표가 직접 발주하는 경우도 있을 수 있어서(가설), 추후 "승인 생략" 옵션은 후순위로 두고 MVP는 승인 단계를 유지합니다(확정).

## 업무 규칙

시스템이 항상 지켜야 하는 규칙 10개입니다. 이 규칙이 데이터 원칙이고, 다음 단계의 ERD와 API가 이를 반영합니다.

| # | 규칙 | 예시 |
| --- | --- | --- |
| R1 | 모든 업무 데이터에 company\_id를 붙이고, 다른 회사 데이터는 조회·수정할 수 없다 | A사 직원이 B사 품목 목록을 볼 수 없음 |
| R2 | 재고 수량은 입출고 이력(InventoryMovements)으로 설명된다 | 현재 97개 = 3/2 +100, 3/5 -3 |
| R3 | 출고 수량이 현재 재고보다 크면 차단한다 (재고는 음수가 될 수 없다) | 재고 40개인데 50개 출고는 오류 |
| R4 | 발주는 DRAFT → APPROVED → ORDERED → RECEIVED 순서로만 바뀔다. 입고 완료 전까지 CANCELLED가 가능하다 | RECEIVED인 발주는 취소할 수 없음 |
| R5 | 발주를 승인(APPROVED)할 수 있는 역할은 관리자다 | 구매 담당자는 초안까지만 작성 |
| R6 | 발주한 품목이 입고되면 발주 수량과 대조하고, 부분 입고를 기록할 수 있다 | 100개 발주 중 60개 입고 시 남은 40개는 미입고로 표시 |
| R7 | 판매 유형 출고는 판매 채널을 함께 기록한다 (스마트스토어, 자사몰, 기타) | 출고 3개, 채널: 스마트스토어 |
| R8 | 재고가 재주문점 이하가 되면 부족 상태로 표시하고 발주 추천 대상으로 올린다 | 재주문점 70, 현재고 65 → 부족 |
| R9 | 출고는 유형(판매, 폐기·파손, 기타)을 함께 기록하고, 발주 추천의 일평균 판매량에는 판매 유형만 포함한다 | 폐기 5개 출고는 재고는 줄이지만 판매량에는 넣지 않음 |
| R10 | 실사 차이는 재고 숫자를 직접 고치지 않고 사유가 있는 "조정" 이력으로 기록한다. 조정 후에도 재고는 음수가 될 수 없다 | 시스템 50개, 실제 47개 → 조정 −3 (사유: 실사 차이) |

R4의 "입고 완료 전까지 취소 가능"과 R6의 부분 입고는 제가 정한 초안이라, 부분 입고 후에는 취소를 허용하지 않기로 확정했습니다(MVP).

## 요구사항

MVP 필수 기능 7개를 "누가 무엇을 하고 싶은지"(사용자 스토리)와 "되면 완료"(완료 기준)로 풀었습니다. 완료 기준이 구현·테스트의 기준이 됩니다. 이 7개는 모두 Must이고, AX 기능(발주 추천 등)은 다음 단계인 AX 설계에서 따로 정합니다.

| ID | 기능 | 사용자 스토리 | 완료 기준 | 관련 규칙 |
| --- | --- | --- | --- | --- |
| F1 | 회사/사용자 | 대표로서 직원을 초대하고 역할을 정해, 각자 맞는 화면만 보게 한다 | 로그인하면 자기 회사 데이터만 보이고, 역할별로 허용된 화면만 열린다 | R1, R5 |
| F2 | 공급업체 | 구매 담당자로서 공급업체를 등록하고 납기·단가를 기록해 두고 싶다 | 업체를 등록·조회·수정할 수 있고, 발주를 하면 업체별 약속 납기·단가가 이력으로 남는다 | R1 |
| F3 | 품목(SKU) | 구매 담당자로서 품목별 단가, 안전재고, 기본 공급업체를 저장해 두고 싶다 | 품목을 등록·수정할 수 있고, 안전재고와 기본 공급업체가 품목에 저장되고, 리드타임은 기본 공급업체의 값을 쓴다 | R1, R8 |
| F4 | 입고/출고 | 창고 담당자로서 상품이 들어오고 나갈 때 바로 기록하고 싶다 | 입고·출고를 등록하면 재고가 즐시 바뀌고 이력이 남는다. 재고보다 큰 출고는 오류가 난다. 출고에는 판매 채널이 기록된다 | R2, R3, R7, R9, R10 |
| F5 | 현재 재고 | 모든 역할로서 품목별 지금 재고와 상태를 한 화면에서 보고 싶다 | 품목별 현재고와 상태(정상/부족)가 보이고, 수량이 입출고 이력 합계와 일치한다 | R2, R8 |
| F6 | 발주 | 구매 담당자로서 발주서를 작성하고, 대표가 승인해 입고까지 이어지게 하고 싶다 | 발주를 만들고 상태를 바꿀 수 있고, 허용되지 않는 상태 이동은 막히며, 입고 등록이 발주와 연결된다 | R4, R5, R6 |
| F7 | 대시보드 | 대표로서 지금 무엇이 위험한지 한눈에 보고 싶다 | 재고 부족 품목, 장기재고, 이번 달 입출고 현황이 한 화면에 표시된다 | R2, R8 |

장기재고의 기준(몇 개월 무출고인지)은 아직 정하지 않았습니다. 인터뷰에서 업종별로 확인한 뒤 품목이나 회사 설정값으로 두는 방향을 검토합니다.

## 기능별 세부 요구사항

기능마다 입력 항목(\* 표시는 필수)과 지켜야 할 검증·예외 처리를 정리했습니다. 항목은 제안서(품목에 단가·안전재고·리드타임)를 바탕으로 제가 초안을 쓴 것이며, ERD 설계 때 확정합니다. 내부 식별 번호와 company\_id, 생성일 같은 시스템 항목은 적지 않았습니다.

| 기능 | 입력 항목 | 검증·예외 처리 |
| --- | --- | --- |
| F1 회사/사용자 | 회사명\*, 사용자 이름\*, 이메일\*(로그인 ID), 비밀번호\*, 역할\* | 이메일은 중복 불가. 역할은 관리자·구매·재고 담당·창고 담당 중 하나. 마지막 관리자는 역할을 바꾸거나 삭제할 수 없음. 권한 없는 화면 접근 시 차단 메시지 |
| F2 공급업체 | 업체명\*, 담당자, 연락처, 이메일, 리드타임(일)\*, 메모 | 업체명은 회사 안에서 중복 불가. 리드타임은 0 이상 정수. 발주 이력이 있는 업체는 삭제 대신 비활성(is\_active) 처리(확정), 비활성 업체는 새 발주 선택 목록에서만 숨김. 납기·단가 이력은 발주와 입고에서 자동 기록(약속 납기와 실제 입고일, 발주 단가) |
| F3 품목 | 품목명\*, SKU 코드\*, 단위\*, 구매 단가\*, 안전재고(기본 0), 기본 공급업체\* | SKU 코드는 회사 안에서 중복 불가. 단가·안전재고는 0 이상 숫자. 리드타임은 품목이 아니라 기본 공급업체의 값을 사용(확정). 입출고 이력이 있는 품목은 삭제 대신 비활성(is\_active) 처리(확정). 기본 공급업체는 필수이며 발주서 초안을 업체별로 묶고 리드타임을 정하는 데 쓰인다(확정) |
| F4 입고 | 품목\*, 수량\*, 입고일(기본 오늘), 연결 발주(선택, 없으면 직접 입고), 메모 | 수량은 1 이상 정수. 발주 수량을 넘기는 입고는 차단하고 안내 메시지 표시(확정). 부분 입고는 남은 수량 표시. 등록이 끝나면 재고가 즐시 증가하고 이력 생성 |
| F4 출고 | 품목\*, 수량\*, 출고일(기본 오늘), 출고 유형\*(판매/폐기·파손/기타), 판매 채널(유형이 판매일 때 필수, 스마트스토어/자사몰/기타)(제안), 메모 | 수량은 1 이상 정수. 현재고보다 큰 출고는 차단하고 현재고를 메시지에 표시(R3). 등록 후 재고가 즐시 감소하고 이력 생성 |
| F4 조정 | 품목\*, 조정 수량\*(늘리면 +, 줄이면 −), 조정일(기본 오늘), 사유\*, 메모 | 실사로 센 재고가 시스템과 다를 때 입출고 이력에 "조정" 유형으로 기록한다(확정). 재고 숫자를 직접 고치지 않으므로 재고 = 이력 합계(R2)가 유지된다. 사유는 필수. 조정 후 재고가 음수가 되면 차단(R3). 발주 추천의 판매량에는 포함하지 않는다. 입력 위치는 출고 등록 화면의 유형 선택(제안) |
| F5 현재 재고 | (조회 전용) 품목, 현재고, 상태, 마지막 입출고일 | 현재고는 이력 합계와 항상 같아야 함(R2). 상태는 정상/부족 두 가지(R8). 품목명·SKU로 검색, 상태로 필터 |
| F6 발주 | 공급업체\*, 발주 품목 행(품목\*, 수량\*, 단가\*), 희망 납기, 메모 / 발주번호·작성자·승인자는 자동 | 품목 행이 1개 이상이어야 저장. 수량은 1 이상. 상태는 R4의 순서로만 변경. 승인은 관리자만(R5). 승인 후에는 품목·수량 수정 불가(제안). 입고 완료 전까지만 취소 가능(부분 입고가 한 번이라도 있으면 불가, 확정) |
| F7 대시보드 | (조회 전용) 재고 부족 품목 수·목록, 장기재고 품목, 이번 달 입고·출고 수량 | 데이터가 없으면 "아직 데이터가 없습니다"와 품목 등록 안내. 장기재고 기준은 열린 질문 |

표의 "제안"이라고 적은 항목은 제안서에 없는 제 판단이라, 인터뷰와 설계에서 다시 확인합니다.

## 업무 흐름

&#91;embedded content: 업무 흐름 · 재고 확인에서 발주, 입고, 출고까지\]

위쪽 줄은 재고 확인에서 발주 승인까지, 아래 줄은 입고와 출고가 현재 재고를 바꾸고 다시 재고 확인으로 이어지는 과정입니다. 재주문점 이하일 때만 발주가 시작되고(R8), 발주 상태는 R4의 순서로만 움직이며, 재고보다 큰 출고는 막습니다(R3).

## 역할별 업무 흐름

&#91;embedded content: 역할별 업무 흐름 · 레인 3개, 단계 6개\]

역할 간 넘김이 한 곳에 있습니다. 구매 담당이 발주서를 만들면 관리자가 승인하고, 승인된 발주를 구매 담당이 공급업체에 내보내면, 상품이 도착했을 때 창고 담당이 입고를 등록합니다. 출고는 판매가 생길 때마다 창고 담당이 등록하고, 재고가 줄면 구매 담당이 다시 확인합니다.

| 화면 | 하는 일 | 접근 역할 | 기능 |
| --- | --- | --- | --- |
| 로그인 | 계정으로 들어가면 자기 회사 데이터만 열림 | 전체 | F1 |

| 재고 현황 | 품목별 현재고와 상태(정상/부족), 입출고 이력 보기 | 전체 | F5 |
| 품목 | 품목 목록, 등록·수정(단가, 안전재고, 기본 공급업체) | 관리자, 구매·재고 담당 (창고 담당은 조회) | F3 |
| 공급업체 | 목록, 등록·수정, 납기·단가 이력 | 관리자, 구매·재고 담당 (창고 담당은 조회) | F2 |
| 입고 등록 | 입고 수량을 등록하고 발주와 연결(부분 입고 가능) | 전체 | F4, F6 |
| 출고 등록 | 수량과 판매 채널 입력, 재고보다 크면 오류 | 전체 | F4 |
| 발주 | 목록, 작성, 상태 변경, 승인 | 관리자, 구매·재고 담당 (승인은 관리자만) | F6 |
| 사용자 관리 | 직원 초대, 역할 지정 | 관리자만 | F1 |

## 화면별 상세

화면마다 보이는 것, 할 수 있는 일, 데이터가 없거나 오류가 났을 때의 모습을 정리했습니다. 레이아웃 그림은 그리지 않고, 이 내용을 바탕으로 화면 설계와 구현을 진행합니다.

| 화면 | 보이는 것 | 할 수 있는 일 | 빈 화면·오류 |
| --- | --- | --- | --- |
| 로그인 | 이메일·비밀번호 입력칸 | 로그인 | 틀린 정보면 "이메일 또는 비밀번호가 맞지 않습니다" |
| 대시보드 | 재고 부족 품목 수와 목록, 장기재고 품목, 이번 달 입고·출고 수량 | 부족 품목을 눌러 재고 현황이나 발주 작성으로 이동 | 데이터 없음: "아직 데이터가 없습니다"와 품목 등록 안내 |
| 재고 현황 | 품목별 현재고, 상태(정상/부족), 마지막 입출고일 | 검색, 상태 필터, 품목을 눌러 입출고 이력 보기 | 검색 결과 없음: "일치하는 품목이 없습니다" |
| 품목 | 품목 목록(이름, SKU, 단가, 안전재고, 기본 공급업체) | 등록, 수정, 비활성(창고 담당은 보기만) | SKU 중복 시 "이미 사용 중인 SKU 코드입니다" |
| 공급업체 | 업체 목록(리드타임 포함), 업체별 납기·단가 이력 | 등록, 수정, 비활성(창고 담당은 보기만) | 이력 없음: "아직 발주 이력이 없습니다" |
| 입고 등록 | 입고 대기 발주 목록, 발주별 미입고 수량 | 발주를 고르거나 '직접 입고'를 선택해 입고 수량 입력(부분 입고 가능) | 대기 발주 없음: "입고할 발주가 없습니다". 초과 입고는 차단하고 안내 메시지 표시 |
| 출고 등록 | 품목 선택, 현재고 표시, 유형(판매/폐기·파손/기타/재고 조정)·수량·판매 채널 입력(제안) | 출고 등록 | 재고 부족: "현재고(40개)보다 많이 출고할 수 없습니다" |
| 발주 | 발주 목록(번호, 업체, 상태, 작성자), 발주 상세 | 작성, 상태 변경, 승인(관리자만), 취소 | 권한 없는 승인 시도: "관리자만 승인할 수 있습니다". 허용되지 않는 상태 변경은 막히고 이유 표시 |
| 사용자 관리 | 사용자 목록(이름, 이메일, 역할) | 초대, 역할 변경, 비활성 | 마지막 관리자 변경 시: "관리자가 최소 1명 필요합니다" |

오류 메시지 문구는 예시이며, 구현 단계에서 다듬습니다.

## 사용자 시나리오

대표 시나리오는 제안서의 사용자 테스트 흐름(품목 등록 → 입고 → 출고 → 부족 확인 → 발주 생성)에 공급업체 등록과 승인·입고를 붙여 9단계로 펼 것입니다. 이 시나리오가 사용자 테스트의 스크립트가 되고, 숨은 숫자는 모두 예시입니다.

**예시 숫자.** 품목 "A 티셔츠 검정/M"(SKU TS-BK-M), 구매 단가 8,000원, 안전재고 20개, 기본 공급업체(리드타임 5일) "가나 상사". 재주문점은 일평균 판매량 10개를 가정해 10 × 5 + 20 = 70개입니다. 실제 일평균 판매량 계산 방법은 AX 설계에서 정합니다.

| 단계 | 역할 | 화면 | 행동 | 시스템 결과 | 규칙 |
| --- | --- | --- | --- | --- | --- |
| 1 | 구매·재고 담당 | 공급업체 | "가나 상사"(리드타임 5일) 등록 | 공급업체 목록에 표시 | R1 |
| 2 | 구매·재고 담당 | 품목 | 품목 등록(위 예시 값, 기본 공급업체 가나 상사) | 품목 목록에 표시, 현재고 0 | R1 |
| 3 | 창고 담당 | 입고 등록 | 발주 없이 직접 입고 100개 | 현재고 100, 이력 "+100" | R2 |
| 4 | 창고 담당 | 출고 등록 | 35개 출고, 채널 스마트스토어 | 현재고 65, 이력 "-35"에 채널 기록 | R2, R7 |
| 5 | 시스템 | 재고 현황, 대시보드 | 없음(자동) | 현재고 65가 재주문점 70 이하라 상태가 "부족"으로 바뀔 | R8 |
| 6 | 구매·재고 담당 | 발주 | 대시보드의 부족 품목에서 발주서 작성(가나 상사, 60개, 단가 8,000원) | 발주 상태 DRAFT | R4 |
| 7 | 관리자 | 발주 | 발주 승인 | 상태 APPROVED | R5 |
| 8 | 구매·재고 담당 | 발주 | 공급업체에 발주했다고 표시 | 상태 ORDERED | R4 |
| 9 | 창고 담당 | 입고 등록 | 발주를 고르고 60개 입고 | 현재고 125(65 + 60), 상태 "정상", 발주 RECEIVED, 약속 납기와 실제 입고일이 공급업체 이력에 기록 | R2, R6 |

**예외 시나리오.** 정상 흐름뿐 아니라 아래 세 가지도 같이 테스트합니다.

| 상황 | 기대 결과 | 규칙 |
| --- | --- | --- |
| 4단계 뒤 현재고 65인데 창고 담당이 80개 출고를 등록 | "현재고(65개)보다 많이 출고할 수 없습니다"라는 메시지가 뜨고 재고·이력은 바뀔지 않음 | R3 |
| 6단계 뒤 구매 담당이 직접 승인을 시도 | 승인이 막히고 "관리자만 승인할 수 있습니다"라는 메시지가 뜨며 상태는 DRAFT 유지. 화면 버튼만 숨기는 것으로는 부족하고 서버에서도 차단해야 함 | R5 |
| 9단계에서 발주 60개 중 40개만 입고 | 현재고 +40, 미입고 20개 표시, 발주는 전량 입고 전까지 ORDERED 유지(확정) | R6 |

## 열린 질문과 다음 단계

아래 질문 6개 중 장기재고 기준만 남았고 나머지는 2026-11-03에 확정했습니다(체크 표시). 질문마다 지금 임시로 가정한 내용을 함께 적었습니다.

- [x] 입고는 발주 없이도 등록할 수 있나요? (확정: 허용. 초기 재고와 직접 구매분을 위해 '직접 입고'로 구분)
- [x] 부분 입고 후에 남은 수량을 취소할 수 있나요? (확정: MVP에서는 허용하지 않음)
- [x] 대표가 직접 발주할 때 승인 단계를 생략할 수 있나요? (확정: MVP는 승인 단계 유지)
- [x] 리드타임을 품목별로 저장할까, 공급업체별로 저장할까요? (확정: 공급업체별 저장. 품목의 리드타임은 기본 공급업체의 값)
- [ ] 장기재고는 몇 개월 무출고를 기준으로 할까요? (임시: 정하지 않음, 인터뷰에서 확인)
- [x] 실사 후 재고 차이는 어떻게 수정할까요? (확정: 입고·출고 이력에 "조정" 유형으로 기록하고 사유는 필수)
