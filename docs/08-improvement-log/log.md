## 2026-11-04 · Codex 교차 검증 반영: 백엔드 안전 수정 (#71)

출처: 다른 AI(Codex)로 코드를 교차 검증해서 찾은 문제. 항목마다 먼저 실패하는 테스트로 재현한 뒤 고쳤다.

### A. 테스트가 개발 DB를 지울 수 있음

- 문제: 테스트는 시작할 때 `downgrade base`로 표를 모두 지운다. `TEST_DATABASE_URL`에 개발 DB(`scm`) 주소를 잘못 넣으면 개발 데이터가 사라진다.
- 원인: 지우기 전에 접속할 DB가 정말 테스트 DB인지 확인하지 않았다.
- 해결: 초기화 함수(`tests/conftest.py`의 `reset_database`)가 DB 이름이 정확히 `scm_test`가 아니면 아무것도 하지 않고 테스트 전체를 멈춘다(`pytest.exit`).
- 결과: `scm`·`scm_test_old`·`SCM_TEST`·이름 없음 4가지 주소에서 지우기 함수가 한 번도 불리지 않는 것을 테스트로 확인(진짜 DB에는 접속하지 않음).

### B. 관리자 동시 변경으로 활성 관리자 0명

- 문제: 관리자 A, 담당자 B에서 ① B 비활성 요청이 B(담당자)를 읽고 멈춤 → ② B를 관리자로 → ③ A를 담당자로(관리자 2명이라 통과) → ④ ①이 이어서 B 비활성 → 활성 관리자 0명.
- 원인: 대상 직원을 회사 줄 잠금보다 **먼저** 읽고, 그 값("B는 담당자라 검사 필요 없음")으로 판단했다. 잠금도 "관리자를 잃는 변경"일 때만 걸었다.
- 해결: `update_user`가 모든 변경에서 회사 줄을 먼저 잠그고, 그 뒤에 대상 직원을 읽어 검사한다.
- 결과: 위 순서를 재현한 테스트가 고치기 전 활성 관리자 0명으로 실패 → 고친 뒤 1명. 잠금 줄을 빼면 새 테스트와 #24의 동시 강등 테스트가 함께 실패하는 것도 확인.

### C. 여러 줄 입고 "전체 취소" 테스트가 실제 저장 실패를 검증하지 못함

- 문제: 기존 테스트는 둘째 줄이 초과 입고라 쓰기 전 검사에서 끝났다. 첫 줄을 실제로 저장(flush)한 뒤 실패하는 경우는 확인하지 못했다.
- 원인: 실패를 일으키는 위치가 저장 단계보다 앞이었다.
- 해결: 둘째 줄의 `register_movement`에서 강제로 예외를 내고, 실제 API 경로를 진짜 DB 연결로 호출한 뒤 별도 연결에서 이력 수를 센다.
- 결과: 지금 코드는 통과(버그 아님, 테스트 보강). 일부러 줄마다 commit 하도록 바꾸면 이력 1건이 남아 테스트가 실패하는 것을 확인.

### D. 큰 정수 입력이 500

- 문제: 리드타임·수량·단가에 2,147,483,648을 넣거나, 주소·필터·본문의 번호, 쪽 번호가 크면 500.
- 원인: DB 정수 칸 최댓값(2,147,483,647)을 넘는 값이 요청 검사를 통과해 DB에서 `integer out of range`가 났다. 번호 칸도 DB에서 integer 로 바꿔 비교해 같은 오류가 났다.
- 해결: `schemas/common.py`에 상한 있는 칸 타입을 모았다. 리드타임 0~365일, 수량 1~100만 개, 안전재고 0~100만 개, 단가 0~1억 원, 번호는 DB 최댓값까지, 쪽 번호 100만까지.
- 결과: 22가지 요청이 모두 422 + 문제 칸 이름. 상한값은 통과하고 상한 + 1은 막히는지도 테스트.

### E. 문서의 동시성 설명이 구현과 다름

- 문제: `api-design.md`는 상태 변경을 "갱신 구문에 상태 조건"으로 막는다고 적었지만, 구현은 행 잠금 뒤 상태 검사다.
- 해결: 문서를 구현(발주서 행 잠금 → 상태 읽기 → 검사 → 변경)에 맞췄다.

## 2026-11-04 · Codex 교차 검증 반영: 화면 수정 (#73)

출처: 다른 AI(Codex)로 코드를 교차 검증해서 찾은 문제 중 프론트 3개.

- 문제 A: 입출고·입고·정정 폼에서 "등록"을 빠르게 두 번 누르면 같은 요청이 두 번 들어갈 수 있다.
  - 원인: 제출 중인지 상태값(useState)으로만 막으면 상태는 다음 화면 갱신 뒤에야 바뀌어, 그 전에 들어온 두 번째 제출이 통과한다.
  - 해결: 제출 함수 맨 앞에서 ref(`sending`)를 즉시 확인해 버리고, 버튼은 `busy` 상태로 잠가 "등록 중…"을 보여 준다. 성공·실패 모두 `finally`에서 풀고 입력값은 지우지 않는다.
  - 결과: 같은 순간 제출을 두 번 보내도 서버 요청은 1건(입출고 폼·정정 폼을 브라우저에서 확인).
- 문제 B: 비활성 품목은 입출고 등록 화면의 품목 목록에 없어 입고·출고·조정을 할 수 없다(데이터 원칙 8 위반).
  - 원인: 목록을 `include_inactive` 없이 불러왔다.
  - 해결: 입출고 폼은 비활성 포함으로 불러오고 이름 옆에 "(비활성)"을 붙인다. 발주서 작성은 그대로 활성만.
  - 결과: 비활성으로 바꾼 품목이 "BAG-EC · 에코백 (비활성)"으로 선택 가능.
- 문제 C: 로그인 확인(/me)이 401이 아닌 이유(네트워크·500)로 실패하면 화면이 "불러오는 중…"에서 멈춘다.
  - 원인: 실패를 삼키고(`catch(() => {})`) 안내가 없었다.
  - 해결: 401이 아닌 실패는 오류 문장과 "다시 시도" 버튼을 보여 준다. 401은 기존처럼 로그인 화면으로.
  - 결과: 백엔드를 끄면 안내가 뜨고, 켠 뒤 "다시 시도"로 화면이 열린다.

## 2026-11-04 · 추천 수량 float 오차 (#38)

- 문제: 설계 예시 코드(`architecture.md`)대로 `판매 ÷ 30`을 float로 계산하면, 판매 31·리드타임 16·안전재고 0·가용재고 0에서 추천 수량이 31이 아니라 32가 나온다.
- 원인: 31/30을 float로 정확히 저장할 수 없어 31/30 × 30 = 31.000000000000004가 되고, 올림(ceil)이 이 작은 오차를 1개로 키운다. 판매 1~399·리드타임 0~39·안전재고 0~29 조합 중 1,050건이 틀렸다.
- 해결: 일평균·재주문점·올림 전 수량을 `fractions.Fraction`(정확한 분수)으로 계산하고 마지막에만 올림한다. 표준 라이브러리라 의존성 추가는 없다.
- 결과: `test_exact_integer_is_not_over_ceiled`가 31을 확인하고, 분수를 float로 되돌리면 이 테스트가 실패한다.

## 2026-11-05 · 추천 초안 동시 요청 (#40)

- 문제: 같은 공급업체 품목으로 초안 만들기 요청 8건이 동시에 오면, 여러 요청이 동시에 "이 업체의 DRAFT 없음"을 보고 각자 새 발주서를 만들려다 고유 제약 오류(UniqueViolation, 500)로 실패한다.
- 원인: "DRAFT가 있는지 읽기 → 없으면 만들기" 사이에 다른 요청이 끼어들 수 있다. DRAFT가 아직 없으니 잠글 행도 없다.
- 해결: 초안을 찾기 전에 회사 행을 먼저 잠가(잠금 순서 회사 → 발주서 → 품목) 요청을 한 줄로 세우고, 저장 확정(commit)은 요청 끝에 한 번만 한다.
- 결과: 동시 8건(다른 품목) → 발주서 1장에 8줄, 같은 품목 8건 → 1건 성공·7건 409 `DUPLICATE_ITEM`. 잠금을 빼면 두 테스트가 고유 제약 오류로 실패하는 것을 확인했다. 업체 2곳 중 둘째에서 막히면 첫째 업체 초안도 저장되지 않는다.

## 2026-11-05 · 재고 상태 계산의 순환 import (#76)

- 문제: 재고 목록(`GET /stock`)에 부족·정상 상태를 붙이는 코드를 `services/stock.py`에 두면, 추천 계산을 불러오는 순간 파일끼리 서로를 불러오는 고리(순환 import)가 생겨 서버가 시작되지 않는다.
- 원인: `stock` → `recommendations` → `purchase_orders` → `stock` 순서로 파일끼리 서로를 불러오는 고리가 생겼다(발주 입고가 `stock.register_movement`를 쓰기 때문).

- 결과: 고리가 없어졌고, 재고 목록·대시보드·추천 목록이 같은 함수로 같은 답을 낸다(경계값 재주문점 70 = 현재고 70에서 세 곳 모두 "부족").

## 2026-11-05 · Codex 교차 검증 반영: 추천 계산 시점·초안 재검사·N+1 (#84)

6주차 코드(#75·#77~#80)를 Codex로 교차 검증해 4건이 나왔다.

### A. 현재고와 진행 중 수량을 서로 다른 순간에 읽음
- 문제: 현재고 0·진행 중 100(가용재고 100, 추천 없음)인 품목에서, 추천 조회가 현재고를 읽은 직후 다른 요청이 100개를 전량 입고하면 추천 170이 나왔다.
- 원인: PostgreSQL 기본 격리 수준(READ COMMITTED)은 문장마다 그 순간의 확정 데이터를 읽는다. 현재고는 입고 전(0), 진행 중 수량은 입고 후(0)를 읽어 가용재고가 0이 됐다.
- 해결: 추천·재고·대시보드 조회 경로만 REPEATABLE READ 세션(`ReadDB`)을 써서 첫 조회 순간의 모습으로 끝까지 읽는다.
- 결과: 두 조회 사이에 입고를 끼워 넣는 테스트가 추천 없음을 확인한다. 격리 수준을 되돌리면 이 테스트가 실패한다.

### B. 초안 만들기가 잠그기 전에 검사·계산
- 문제: 추천 170을 계산한 직후 입고 100이 확정되거나 품목이 비활성이 돼도, 옛 계산으로 초안이 만들어졌다.
- 원인: 검사·계산을 회사 행 잠금보다 먼저 했고, 품목은 잠그지 않았다.
- 해결: 회사 → 회사의 DRAFT → 요청 품목(번호 순) 순으로 잠근 뒤 검사·계산한다.
- 결과: 입고·비활성 변경이 끼어드는 두 테스트가 409(`NOT_RECOMMENDED`·`INACTIVE_REFERENCE`)를 확인한다. 고치기 전 코드로 돌리면 둘 다 실패한다. 입고는 이력 INSERT의 외래 키가 회사 행을 잡아 회사 잠금만으로도 기다리지만, 비활성 변경은 품목 잠금을 빼면 테스트가 실패한다.

### C. 품목 검사 N+1
- 문제: 초안 만들기의 쿼리 수가 품목 3개 20번, 30개 47번으로 품목 수만큼 늘었다.
- 원인: 품목 검사(`check_items`)가 품목마다 한 번씩 조회했다.
- 해결: 요청 품목을 `IN` 조건으로 한 번에 조회한다(발주서 작성·수정도 같은 함수).
- 결과: 3개와 30개의 쿼리 수가 같은지 세는 테스트를 추가했다.

### D. "오늘 판매 포함" 테스트 빈틈
- 문제: 최근 30일 조건 `<= 오늘`을 `< 오늘`로 망가뜨려도 테스트 269개가 모두 통과했다.
- 원인: 오늘 판매만 있는 품목을 확인하는 테스트가 없었다.
- 해결·결과: 오늘 판매 30 → 일평균 1, 추천 39를 확인하는 테스트를 추가했고, 변형을 넣으면 실패한다.

## 2026-11-05 · 발주서 상세에서 금액과 입고 잔량 확인 (#93)

- 문제: 발주서 상세에서 공급업체와 납기를 기록 사이에서 찾아야 했고, 품목별 금액과 발주 합계가 없었다.
- 원인: 핵심 정보와 보조 기록이 같은 크기로 나열됐고, 입고량과 남은 수량이 서로 다른 칸에 있었다.
- 해결: 핵심 정보를 상단 카드에 모으고, 승인·발주·입고·취소 기록을 제목과 날짜가 있는 칸으로 분리했다. 메모는 기록 아래에 따로 배치했다. 품목별 입고 현황과 발주 금액은 표에 표시하고, 합계는 `BigInt`로 계산한다.
- 결과: Node로 최대 줄 금액, 일반 숫자의 안전 정수 범위를 넘는 합계, 서울 날짜 기준 납기 경계를 확인했다.
