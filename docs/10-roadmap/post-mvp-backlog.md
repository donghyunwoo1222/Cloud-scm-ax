## 자동화 확장: 입구(가져오기)와 출구(발주서 전달) (MVP 범위 밖, 2026-11-09 결정)

지금은 가운데(부족 감지, 추천, 초안, 승인)만 만들어져 있다. 판매 데이터가 사람 손으로 들어오고 발주서가 시스템 밖으로 사람 손으로 나간다. 직접 입력을 줄이기 위해 양 끝을 채운다. 팩스는 제외한다.

```
파일 올리기(판매·품목·입고) → 부족 감지 → 추천 → 초안 → 승인 → 발주서 문서 → 메일 발송(반자동) → 입고
```

### 확정한 결정
| 영역 | 결정 |
| --- | --- |
| 가져오기 형식 | CSV(UTF-8 BOM 포함)와 .xlsx. 입고 명세 PDF는 제외(표 인식 오류가 재고로 번지는 위험) |
| 샘플 파일의 역할 | `data/sample-orders-smartstore-like.csv`는 참고용 예시일 뿐이다. 특정 쇼핑몰의 열 이름, 상태 값, 상품 코드에 맞춰 만들지 않고, 어떤 파일이든 사용자가 열을 지정하는 방식으로 만든다 |
| 열 지정 | 올릴 때 사용자가 "상품 코드 열, 수량 열, 날짜 열, 고유 주문번호 열, (선택) 상태 열"을 고른다. 파일 머리글 이름이 비슷하면 미리 골라 둔다 |
| 품목 식별 | 지정한 상품 코드 열을 `products.sku`와 맞춘다. 맞는 SKU가 없는 행은 미리보기에서 막는다. SKU는 재고를 따로 세는 최소 단위이므로 옵션(색상·사이즈)이 다르면 SKU를 나눠 등록한다. 한 상품 코드에 옵션 값이 2종 이상 섞여 있으면 미리보기에서 "N종이 하나의 SKU로 합산됩니다"라고 경고한다. "상품 코드+옵션"을 SKU에 연결하는 기능은 저장 자리가 필요해 실사용과 인터뷰 후 판단한다 |
| 반영 불가 행 | 미등록 SKU, 재고가 음수가 되는 출고 행(날짜순 적용 기준)은 문제 행이다. 문제 행이 있으면 기본은 반영 불가이고, 사용자가 "문제 행 N건 제외하고 반영"을 직접 체크해야 한다. 가져오기 되돌리기는 1차에 만들지 않고 미리보기(요약, 날짜 범위, 총 수량)를 안전장치로 삼는다 |
| 가져오기 제한 | 5MB, 5,000행 이하. 수취인·주소·송장 열은 읽지 않고, 파일은 디스크에 저장하지 않고 메모리에서만 처리한다. 권한은 같은 작업을 손으로 하는 권한을 따른다 |
| 판매 반영 기준 | 상태 열을 지정하면 그 열의 값 목록을 보여 주고 사용자가 "반영할 값"을 체크한다("배송 중", "배송완료"처럼 출고가 끝난 값을 권장). 상태 열이 없으면 모든 행을 반영한다. 체크하지 않은 값은 건너뛰고 미리보기에 사유를 보여 준다(이력은 수정 불가라 취소 정정을 줄이려는 것) |
| 날짜 열 | 사용자가 지정한 날짜 열을 그대로 `movement_date`로 쓴다. 주문일인지 발송일인지는 사용자가 고르고, 파일에 발송일이 없으면 주문일을 쓴다. 상태 값은 우리 DB에 저장하지 않고 거르는 용도로만 쓴다(우리 시스템에는 배송 상태가 없고, 재고는 물건이 나간 시점에 줄어든다) |
| 중복 방지 | 지정한 고유 주문번호 열 값을 `inventory_movements.external_ref`(외부 주문번호) 칸 하나에 저장하고 회사+값이 유일하도록 제한. 새 표는 두지 않는다(표 7개 유지) |
| 품목·입고 가져오기 (#155, 2026-11-09) | 입고 파일 하나로 새 품목 등록 + 직접 입고를 한 트랜잭션에 처리(사용자가 여러 번 일하지 않게). 수량 열이 없으면 품목만 등록. 기존 품목 정보는 고치지 않는다. `external_ref` 유일 제한은 (회사, 유형, 번호). 번호 열이 없으면 날짜·SKU·수량으로 번호를 만든다. 파일 하나에 공급업체는 한 곳: 공급업체 열이 섞이면 오류로 나눠 올리게 한다. 열 지정 기억·모든 행에 같은 값·발주서 매칭은 하지 않았다 |
| 열 매핑 | 저장하지 않고 올릴 때마다 고른다. 사용 빈도를 보고 저장 여부를 다시 정한다 |
| 반영 방식 | 미리보기(반영 N건, 건너뜀 N건, 미등록 SKU, 재고 부족 행) → 확인 → 한 번에 전체 반영(트랜잭션) |
| 판매 채널 | 올릴 때 사용자가 한 번 고른다(출고 시 채널 기록 원칙 유지) |
| LLM | 열 이름 추측과 메일 작성에 쓰지 않는다. 열 추측은 후순위, 메일 문장 다듬기는 C1 |
| 회사 정보 칸 | `companies`에 사업자등록번호, 대표자, 주소, 대표 연락처 추가(선택 입력) |
| 발주서 칸 | `purchase_orders.delivery_address`(비면 회사 주소), `payment_terms`(지불조건). `suppliers.payment_terms`를 기본값으로 두고 발주서에서 수정 가능 |
| 금액 | 단가는 부가세 별도, 부가세 10% 고정, 줄별 세액 없이 공급가액 합계에 한 번 계산 |
| 발주서 문서 | 인쇄·PDF 저장 화면과 엑셀 내보내기를 먼저. 서버 PDF 생성은 메일 첨부 이슈에서 라이브러리와 함께 확인받는다 |
| 메일 | 반자동(버튼, 미리보기, 확인창). 고정 템플릿이며 사용자는 앞머리 한 문단만 고친다. SMTP로 시작. 발송 성공 시 ORDERED, 실패 시 APPROVED 유지. `purchase_orders`에 발송 시각과 수신 주소 칸 추가. 구현(#158): SMTP 는 표준 `smtplib`, 첨부 PDF 는 `fpdf2` + 나눔고딕 동봉(WeasyPrint·헤드리스 Chrome 은 도커 이미지가 수백 MB 늘어 제외), 보내는 주소는 시스템 주소 하나 + Reply-To 담당자, 발송자(`emailed_by`)도 남긴다 |

### 구현 순서(이슈 단위)
1. 판매 가져오기 기반(파일 올리기, 열 선택, 미리보기, 전체 반영, `external_ref`)
2. 품목·입고 가져오기(1번 틀 재사용)
3. 회사 정보 확장과 설정 화면
4. 발주서 문서(인쇄·PDF 저장, 엑셀)
5. 메일 반자동 발송(발송 기록 칸, PDF 첨부)
6. 부족 알림(선택)

새 라이브러리(.xlsx 읽기·쓰기, PDF 생성, SMTP)는 해당 이슈를 시작할 때 이유를 알리고 확인을 받는다. 인터뷰(#46)에서 "발주를 어떻게 전달하세요?", "판매는 어떻게 기록하세요?"를 묻는다.

## 열린 질문

docs/03-planning/service-planning.md §열린 질문과 다음 단계에 나온 질문 중, 구현 시점에 정해야 하는 항목입니다. 각 질문 옆은 해당 문서에 적힌 임시 가정입니다.

- 입고는 발주 없이도 등록할 수 있나요? (임시: 허용. 초기 재고와 직접 구매분을 위해 '직접 입고'로 구분)
- 부분 입고 후에 남은 수량을 취소할 수 있나요? (임시: 허용하지 않음, R4와 R6 충돌 방지)
- 대표가 직접 발주할 때 승인 단계를 생략할 수 있나요? (임시: MVP는 승인 단계 유지)
- 리드타임을 품목별로 저장할까, 공급업체별로 저장할까요? (임시: 품목별, 제안서 기준. 납기 이력은 공급업체별)
- 장기재고는 몇 개월 무출고를 기준으로 할까요? (임시: 정하지 않음, 인터뷰에서 확인)
- 실사 후 재고 차이는 어떻게 수정할까요? (임시: 입고·출고 이력에 "조정" 유형을 더하는 방법을 검토. 제안서 MVP 목록에는 없음)
